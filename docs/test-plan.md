# План перевірок EcoShare (Test Plan)

## 1. Загальна інформація

Цей документ визначає сценарії тестування, очікувані результати та фактичні результати перевірки програмного проєкту EcoShare в межах лабораторної роботи №4 «Розробка базової структури коду».

Метою тестування є перевірка правильності роботи базових класів, серверних модулів, API, демонстраційних даних та клієнтської частини застосунку.

Тестування охоплює:
- Перевірку наслідування класів Guest і Resident.
- Перевірку створення та валідації оголошень.
- Перевірку роботи сервісу Listings із репозиторієм.
- Фільтрацію оголошень за станами.
- Перевірку серверних API-ендпоінтів.
- Перевірку пошуку оголошень.
- Перевірку захисту приватних даних користувачів.
- Перевірку збірки React.
- Перевірку Prisma-схеми.
- Автоматичне тестування через GitHub Actions.

## 3. Методологія тестування

У проєкті EcoShare використовуються такі підходи до перевірки програмного забезпечення:

**1. Доменне тестування**

Перевіряється логіка класів, їхні властивості, наслідування, валідація даних і взаємодія сервісів через контракти.

**2. API-тестування**

Перевіряються HTTP-запити до сервера NestJS, статуси відповідей, структура JSON-даних, робота пошуку та захист приватної інформації.

**3. Ручне тестування**

Перевіряються запуск сервера, отримання демонстраційних оголошень і пошук через API.

**4. Автоматизована перевірка CI**

Для автоматичної перевірки використовується GitHub Actions. Після відправлення змін до GitHub запускаються серверні тести, збірка клієнта та перевірка Prisma-схеми.

## 4. Демонстраційні тестові дані

Для перевірки роботи модуля Listings створено чотири демонстраційні оголошення.

| Назва оголошення | Статус | Очікувана поведінка |
| :--- | :--- | :--- |
| Дриль Bosch | `available` | Відображається у стрічці та знаходиться через пошук. |
| Книга з програмування | `reserved` | Відображається у стрічці зі статусом бронювання. |
| Приховане оголошення | `hidden` | Не відображається у загальній стрічці. |
| Закрите оголошення | `closed` | Не відображається у загальній стрічці. |

Демонстраційні дані зберігаються в пам'яті серверного процесу.

Із чотирьох записів у публічній стрічці повинні відображатися два оголошення зі статусами `available` та `reserved`.

## 5. Доменні тести

Очікуваний результат: створення такого оголошення спричиняє помилку валідації.

Результат: успішно.

**Тест 3. Перевірка роботи сервісу через контракт репозиторію**

Перевіряється взаємодія ListingsService з підставним репозиторієм та отримання публічної інформації про власника оголошення.

Очікуваний результат: сервіс повертає оголошення з правильною назвою та ім'ям власника.

Результат: успішно.

**Тест 4. Перевірка фільтрації станів**

Перевіряється обробка оголошень зі статусами `available`, `reserved`, `hidden`, `closed`.

Очікуваний результат: сервіс повертає тільки оголошення зі статусами `available` та `reserved`.

Результат: успішно.

## 6. API-тести

Файл: `tests/api.test.cjs`

Реалізовано шість автоматичних API-тестів.

**Тест 1. Health endpoint returns OK**

Перевіряється відповідь сервера на запит `/api/health`.

Очікуваний результат: HTTP 200, статус `ok`, назва проєкту EcoShare.

Результат: успішно.

**Тест 2. Listings API returns visible listings**

Перевіряється отримання оголошень через `/api/listings`.

Очікуваний результат: HTTP 200 та два оголошення зі статусами `available` і `reserved`.

Результат: успішно.

**Тест 3. Search is case insensitive**

Перевіряється пошук оголошень незалежно від регістру символів.

Очікуваний результат: запит «ДРИЛЬ» повертає одне оголошення — «Дриль Bosch».

Результат: успішно.

**Тест 4. Listings expose only public fields**

Перевіряється набір полів, які повертає API оголошень.

Очікуваний результат: відповідь містить лише передбачені публічні поля.

Результат: успішно.

**Тест 5. Demo user does not expose private data**

Перевіряється відповідь `/api/users/demo`.

Очікуваний результат: HTTP 200, наявність публічного імені користувача та відсутність полів `email` і `contact`.

Результат: успішно.

**Тест 6. Repeated search parameter returns 400**

Перевіряється обробка запиту з двома параметрами `search`.

Очікуваний результат: сервер повертає HTTP 400 Bad Request.

Результат: успішно.

- Автоматичні браузерні тести React поки відсутні.
- Адаптивність інтерфейсу на мобільних пристроях потребує окремого підтвердження.

Отже, результати тестування характеризують саме реалізований функціонал поточної лабораторної роботи.
