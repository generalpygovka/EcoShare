# Перевірки інтеграції EcoShare — ЛР5

## 1. Мета та область перевірок

Мета — зафіксувати початковий стан EcoShare після ЛР4, перевірити інтеграцію компонентів у ЛР5 та зібрати докази виконання функціональних і нефункціональних вимог.

Об’єкти перевірки: NestJS API, React-клієнт, Prisma/PostgreSQL, авторизація та ролі, оголошення, бронювання, сповіщення, модерація і статистика.

Цей документ — **живий журнал перевірок**, а не твердження, що вся функціональність ЛР5 вже реалізована.

## 2. Базовий стан після ЛР4

У гілці `main` перед початком ЛР5 є:
- сервер NestJS із початковими модулями Auth/Users і Listings;
- доменні класи `Guest`, `Resident`, `Listing`;
- чотири демонстраційні оголошення в пам’яті сервера: два видимі (`available`, `reserved`) та два невидимі (`hidden`, `closed`);
- API стрічки та пошуку, React-клієнт із підключенням до API;
- початкова Prisma-схема, без підтвердженої інтеграції постійного зберігання в PostgreSQL;
- 10 автоматичних тестів базової функціональності (4 доменні та 6 API);
- GitHub Actions із перевірками `backend`, `frontend`, `schema`.

Звіт за ЛР4: [docs/test-plan.md](./test-plan.md). План інтеграції ЛР5: [docs/lab5-plan.md](./lab5-plan.md).

## 4. Локальна базова перевірка

Ці пункти позначаються `[x]` лише після фактичного виконання на комп’ютері тестувальника.

- [ ] `node -v` — підтверджено потрібну версію Node.js (для етапу ЛР5 цільова версія — 24).
- [ ] `npm --prefix src/server ci` — встановлення залежностей сервера.
- [ ] `npm --prefix src/server test` — повторний запуск серверних тестів.
- [ ] `npm --prefix src/client ci` — встановлення залежностей клієнта.
- [ ] `npm --prefix src/client run build` — збірка React.
- [ ] Запуск сервера і клієнта та перевірка у браузері.

**Фактичний результат локального запуску:** ще не внесено.
**Дата / версія Node.js / операційна система:** ще не внесено.
**Кількість пройдених тестів / помилок:** ще не внесено.
**Докази (лог, скриншот, посилання):** ще не внесено.

## 5. Сумісність React із поточним API

Перевірити після інтеграції виправлення контракту клієнта і сервера.

| Сценарій | Очікуваний результат | Статус |
| --- | --- | --- |
| Відкриття стрічки | Видно рівно два публічні демонстраційні оголошення | ☐ Не перевірено після виправлення |
| Статус оголошення | `available` / `reserved` показуються українськими підписами | ☐ |
| Власник | На картці відображається `ownerName` | ☐ |
| Пошук `ДРИЛЬ` | Одне оголошення «Дриль Bosch» | ☐ |
| Запит без збігів | Видно повідомлення про відсутність результатів | ☐ |
| API недоступне | Інтерфейс показує помилку, не зависає | ☐ |

Фактичні результати, дату, браузер і скриншоти додати після перевірки.

## 6. Функціональні вимоги ЛР5

**Незавершені пункти залишаються непозначеними.** Для кожного сценарію необхідно описати тестові дані, очікування, фактичний результат і доказ.

- [ ] **FR-01–FR-03.** Реєстрація, активація акаунта, авторизація та профіль.
- [ ] **FR-04–FR-06.** Створення оголошення, валідація (у тому числі фото), редагування і закриття.
- [ ] **FR-07–FR-09.** Стрічка, фільтрація та пошук.
- [ ] **FR-10–FR-12.** Бронювання, запобігання подвійній броні та скасування.
- [ ] **FR-13–FR-15.** Контакт між користувачами, сповіщення й підтвердження передачі.
- [ ] **FR-16.** Автоматичне зняття та поновлення оголошення.
- [ ] **FR-17–FR-19.** Скарги, рішення модератора та тимчасове блокування.
- [ ] **FR-20.** Агрегована статистика для адміністратора.

### Мінімальні негативні сценарії

- [ ] Запит без авторизації до захищеного API відхиляється.
- [ ] Користувач не може редагувати чуже оголошення.
- [ ] Некоректні дані оголошення спричиняють зрозумілу помилку валідації.
- [ ] Повторне бронювання вже заброньованої речі не створює другу активну бронь.
- [ ] Користувач без ролі модератора не має доступу до модераторських дій.
- [ ] Публічні відповіді не розкривають приватні поля користувачів.

## 7. Нефункціональні вимоги ЛР5

Для кожної перевірки потрібно записати метод, середовище, виміряний результат і порівняння з цільовим значенням зі специфікації.

- [ ] **NFR-01.** Час відповіді стрічки та пошуку під навантаженням.
- [ ] **NFR-02.** Доступність сервісу за визначений період спостереження.
- [ ] **NFR-03.** Хешування паролів та HTTPS.
- [ ] **NFR-04.** Серверна перевірка ролей, прав і власника ресурсу.
- [ ] **NFR-05.** Відсутність приватних даних у публічному API.
- [ ] **NFR-06.** Резервне копіювання БД та успішне відновлення.
- [ ] **NFR-07.** Час виконання користувачем сценарію створення оголошення.
- [ ] **NFR-08.** Адаптивність інтерфейсу від 360 px.
- [ ] **NFR-09.** Робота з клавіатури, доступність і контраст.
- [ ] **NFR-10.** Перевірка поведінки системи з 10 000 акаунтів.
- [ ] **NFR-11.** Журнал дій модераторів і політика збереження.
- [ ] **NFR-12.** Перевірка підтримуваних браузерів.

**Обмеження доказів:** короткий локальний запуск не підтверджує місячну доступність сервісу; проходження збірки не підтверджує продуктивність, безпеку чи повноту реалізації функцій.

## 8. Формат фіксації нового результату

Для кожної додаткової перевірки записувати:

| Поле | Що вказати |
| --- | --- |
| ID | FR / NFR або назва інтеграційного сценарію |
| Дата та середовище | Дата, ОС, Node.js, браузер, гілка/коміт |
| Передумови та кроки | Дані, користувацька роль, послідовність дій |
| Очікуваний результат | Що має відбутися |
| Фактичний результат | Що реально відбулося |
| Статус | Пройдено / не пройдено / не перевірено |
| Доказ | Посилання на CI, лог, скриншот або issue |

Виявлений дефект описати кроками відтворення, очікуваною та фактичною поведінкою. Після виправлення — повторити тест.

## 9. Підсумок базової перевірки

Підготовлено перелік тестів і зафіксовано підтверджені результати CI для початкового стану EcoShare. Перевірки GitHub Actions `backend`, `frontend` та `schema` від 17.11.2026 завершилися успішно. Локальні, інтеграційні та подальші FR/NFR-перевірки залишено відкритими до фактичного виконання. Журнал буде доповнюватися після наступних етапів ЛР5.
